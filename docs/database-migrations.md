# Database migrations

The API uses one shared model with two context types, following EF Core's
[multiple-provider guidance](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/providers).
Separate context types let EF select migrations and snapshots within one assembly;
folders alone would not isolate them.

| Provider | Context | Migration directory in `api/JobTracker.Api` |
| --- | --- | --- |
| `Sqlite` (default) | `AppDbContext` | `Migrations/Sqlite` |
| `Postgres` or `PostgreSQL` | `PostgresAppDbContext` | `Migrations/Postgres` |

`PostgresAppDbContext` inherits all model configuration from `AppDbContext`.
Controllers still receive `AppDbContext`; PostgreSQL configuration registers the
derived implementation. Each context has its own model snapshot. Keep both migration
series up to date whenever the shared model changes.

## Existing SQLite databases

The original three migrations and snapshot were moved into `Migrations/Sqlite`.
Their migration IDs, operations and the `__EFMigrationsHistory` table are unchanged.
Existing local databases continue from their recorded migration history; do not
delete the database or reset that history.

`hex(randomblob(...))` belongs to the historical SQLite workflow backfill, not a
column default. It stays in the SQLite migration. The PostgreSQL initial migration
creates the complete current schema in an empty database, so there are no historical
rows to backfill. Application IDs are generated by `Guid.NewGuid()` in C#, and event
IDs have the same C# initializer. PostgreSQL stores these as `uuid`; no database UUID
default or extension is needed. Other defaults (`Unknown`) are generated by EF for
each provider. This change does not copy existing SQLite data to PostgreSQL.

## Commands

Run these PowerShell commands from the repository root. They require .NET 10 and
`dotnet-ef` 10.x (verified with 10.0.9). Build before using `--no-build`, including
after generating a migration so the update command can find it.

### PostgreSQL initial migration

The initial migration is already included. This is the command used to generate it;
do not run it again against the existing series. The placeholder connection is only
for offline generation and requires no running PostgreSQL server.

```powershell
dotnet build api/JobTracker.sln
dotnet ef migrations add InitialCreate --no-build --project api/JobTracker.Api --context PostgresAppDbContext --output-dir Migrations/Postgres -- --DatabaseProvider=Postgres '--ConnectionStrings:DefaultConnection=Host=localhost;Database=jobtracker_migration_design;Username=design'
```

For later model changes, use the same command with a new descriptive migration name
instead of `InitialCreate`, and generate the matching SQLite migration as well.

### Apply to Neon (manual, changes the target database)

Set the connection string in the shell where you execute the command. Railway's
environment variables do not automatically exist in your local shell. Supply an
Npgsql connection string using the actual Neon credentials, for example
`Host=<host>;Database=<database>;Username=<user>;Password=<password>;SSL Mode=VerifyFull`.
Do not commit credentials to configuration files.

```powershell
$env:DatabaseProvider = 'Postgres'
$env:ConnectionStrings__DefaultConnection = '<Neon Npgsql connection string>'
dotnet build api/JobTracker.sln
dotnet ef database update --no-build --project api/JobTracker.Api --context PostgresAppDbContext -- --DatabaseProvider=Postgres
```

Use the PostgreSQL series for a new empty Neon database. Inspect and reconcile any
pre-existing tables before applying the initial migration to an existing database.
There is no automatic production migration at API startup.

### SQLite development

These command-line settings override any PostgreSQL variables left in your shell.
Run from the repository root to target the usual API-local database explicitly.

```powershell
dotnet build api/JobTracker.sln
dotnet ef database update --no-build --project api/JobTracker.Api --context AppDbContext -- --DatabaseProvider=Sqlite '--ConnectionStrings:DefaultConnection=Data Source=api/JobTracker.Api/jobtracker.db'
```

Generate a later SQLite migration with a descriptive name:

```powershell
dotnet ef migrations add DescribeModelChange --no-build --project api/JobTracker.Api --context AppDbContext --output-dir Migrations/Sqlite -- --DatabaseProvider=Sqlite '--ConnectionStrings:DefaultConnection=Data Source=api/JobTracker.Api/jobtracker.db'
```

## Railway settings

No new environment variables are required for migration selection:

```ini
DatabaseProvider=Postgres
ConnectionStrings__DefaultConnection=<Neon Npgsql connection string>
```

Existing authentication and other deployment settings are unchanged. Neither a
`MigrationsAssembly` variable nor a separate migration-history setting is needed.

## Verification

`dotnet build api/JobTracker.sln` and `dotnet test api/JobTracker.sln` validate the API.
Tests apply the SQLite series to isolated in-memory databases, exercise upgrading
historical data, check provider-specific migration/snapshot discovery and detect
pending model changes. PostgreSQL SQL is generated without opening a connection.
Running that SQL against a real PostgreSQL server is a separate deployment check.
