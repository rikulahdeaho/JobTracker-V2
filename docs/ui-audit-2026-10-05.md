components, status vocabulary, Timeline, Next Action, and the separation of hard
dates from suggestions form a recognizable job-search tool. Two Dashboard
presentations undermine that clarity: the Closed count includes unsent
applications, and the High priority label appears even when the appropriate
action is to wait.

returned `[]`. These are zero detector findings, not proof that the React
interface is correct or accessible. The verified issues below come from source
inspection, component rendering, color calculations, and the production build.
No detector false positives needed dismissal.

## Detailed findings

### 1. [P1] Shared colors produce insufficient text contrast

**Category:** Accessibility / Theming.

**Locations:** [theme.ts](../web/src/app/theme.ts), lines 36–55, 325–329,
346–365; [applicationStatus.ts](../web/src/features/applications/utils/applicationStatus.ts),
lines 29 onward. These values feed navigation, buttons, status chips, and
Next Action/reminder chips.

The following normal-size text pairs fall below 4.5:1:

| Text / state | Foreground and background | Ratio |
| --- | --- | --- |
| Dark selected navigation / primary button | White on `#3B82F6` | 3.68:1 |
| Dark sidebar secondary metadata | `#6E6761` on `#181716` | 3.22:1 |
| Light To Apply status | `#0891B2` on its 10% tint over white | 3.27:1 |
| Light Assignment status | `#D97706` on its 10% tint over white | 2.86:1 |
| Light Offer status | `#16A34A` on its 10% tint over white | 2.95:1 |
| Dark secondary Next Action chip | `#7C3AED` on its 12% tint over `#181716` | 2.89:1 |

**Impact:** Low-vision users have difficulty reading stage, next-step, and
navigation information. Displaying text as well as color is good, but the text
must itself remain legible.

**Standard:** [WCAG 1.4.3 Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
These are normal-size labels, so the large-text exception does not apply.

**Recommendation:** Separate semantic foreground tokens from fill/accent tokens.
Use darker semantic text in light mode and lighter text in dark mode; choose a
primary fill/text pair that passes in its normal, hover, and selected states.
Verify each composited surface rather than assuming `.main` is a text color.

**Suggested command:** `$impeccable harden theme accessibility`.

### 2. [P1] Insights exposes unnamed progress bars

**Category:** Accessibility.

**Location:** [InsightsPage.tsx](../web/src/features/insights/InsightsPage.tsx),
lines 69 and 145.

The Response momentum bar and each Status breakdown bar render with
`role="progressbar"` and a numeric value but no accessible name. Rendering two
status fixtures produced three unnamed progress bars. The Data coverage bars
already have labels and provide a pattern to follow.

**Impact:** Assistive technology encounters percentages without a programmatic
connection to the metric or status they describe.

**Standard:** [WCAG 4.1.2 Name, Role, Value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html).

**Recommendation:** Give each bar an `aria-labelledby` pointing to its visible
metric label, or an equivalent specific `aria-label`. Include relevant context
for the value where needed.

**Suggested command:** `$impeccable harden insights accessibility`.

### 3. [P2] Dashboard counts Draft and To Apply applications as Closed

**Category:** Implementation integrity.

**Location:** [DashboardPage.tsx](../web/src/features/dashboard/DashboardPage.tsx),
line 126; displayed at lines 325–328.

`closedCount` is all applications minus Applied, Interviewing, Assignment, and
Offer. Consequently, Draft and ToApply fall into Closed alongside actual closed
outcomes. Rendering one Draft and one ToApply displayed **Closed 2**, followed by
the description “Rejected, ghosted, or withdrawn applications.” The correct
closed count for that fixture is zero.

**Impact:** Users receive an inaccurate account of their search outcomes.
This contradicts the displayed explanation and the status meanings in
[how-it-works.md](how-it-works.md).

**Standard:** Product correctness; not a WCAG finding.

**Recommendation:** Count Rejected, Ghosted, and Withdrawn explicitly. Preserve
the separate meaning of Active hiring processes; do not solve this by treating
drafts as submitted applications. Add a focused regression test for mixed statuses.

**Suggested command:** `$impeccable harden dashboard summaries`.

### 4. [P2] High priority label is unconditional

**Category:** Implementation integrity.

**Location:** [DashboardPage.tsx](../web/src/features/dashboard/DashboardPage.tsx),
lines 62–69 and 146.

The priority candidate list removes only “No action,” so “Wait for response” is
eligible even when `needsAttention` is false. The section always displays a High
priority chip, including its empty state. A fixture containing one newly sent
application rendered both **High priority** and **Wait for response**.

**Impact:** The dashboard suggests urgency where the workflow rules explicitly
call for waiting, weakening users' ability to distinguish actionable work.

**Standard:** Product correctness; not a WCAG finding.

**Recommendation:** Derive the label from the selected action's actual urgency,
or restrict a genuinely high-priority section to actionable candidates and show
an appropriate waiting/clear state otherwise. Cover waiting-only and empty data.

**Suggested command:** `$impeccable clarify dashboard priority states`.

### 5. [P2] Add/Edit lacks semantic submit and error-focus handling

**Category:** Accessibility / Interaction reliability.

**Location:** [ApplicationFormDialog.tsx](../web/src/features/applications/components/ApplicationFormDialog.tsx),
lines 85–105 and 334–339.

Submission is wired only to the footer button's click handler; there is no form
element or submit event. Invalid submission adds field helper text and returns
without moving focus to the first invalid field or announcing an error summary.
The footer remains outside a scrollable body, so a required-field error can be
well above the user's current position. The separate activity dialog already
uses a form.

**Impact:** Enter in a single-line field does not provide conventional form
submission. Users must manually locate errors after attempting to save.
Field labels and error associations are present; the missing piece is recovery.

**Standard:** Keyboard and accessible error-recovery practice. No claim that
Enter-to-submit alone is a WCAG requirement; announcement behavior needs an
interactive assistive-technology check.

**Recommendation:** Use a semantic form with one submit handler, preserving
multiline entry and the fixed footer. On validation failure, expand the necessary
section, then focus and reveal the first invalid field; consider an announced
summary for multiple errors.

**Suggested command:** `$impeccable harden application form`.

### 6. [P2] Visual typography is also determining the document outline

**Category:** Accessibility.

**Locations:** [PageSection.tsx](../web/src/components/ui/PageSection.tsx), lines
37 and 61; [DashboardPage.tsx](../web/src/features/dashboard/DashboardPage.tsx),
lines 297, 320, and 327; the Details page has the same title pattern.

PageHeader renders as `h4` and SectionCard as `h6`; dashboard numeric values also
render as `h4`. The theme does not override MUI's variant-to-element mapping.
The rendered dashboard began H4 → H6 → H5 → H6, followed by number-only H4s,
and contained no H1.

**Impact:** Heading navigation exposes visual sizing choices instead of a clear
page/section hierarchy, including isolated numbers as navigation destinations.

**Standard:** Semantic heading practice; the absence of H1 alone is not asserted
to prove a WCAG failure.

**Recommendation:** Preserve visual variants while setting `component="h1"`
for page titles, H2/H3 for genuine nested sections, and paragraphs/spans for
numeric values. Keep the sidebar brand outside the page's content outline.

**Suggested command:** `$impeccable harden page semantics`.

### 7. [P2] Several controls miss the 44 px touch-target goal

**Category:** Responsive design.

**Locations:** [ApplicationFormDialog.tsx](../web/src/features/applications/components/ApplicationFormDialog.tsx),
lines 279 and 285; [Sidebar.tsx](../web/src/components/layout/Sidebar.tsx), lines
145 and 164; [ApplicationsPage.tsx](../web/src/features/applications/pages/ApplicationsPage.tsx),
lines 98–107; [theme.ts](../web/src/app/theme.ts), line 199 onward.

Small text buttons and small filter toggles inherit MUI padding and line-height
without a minimum target height override. At the default root font size, their
declared styles yield approximately 34–40 px heights. This is a CSS-derived
finding, not a browser-measured bounding-box result. Navigation rows and inputs
already establish 48 px minimum heights.

**Impact:** Compact controls require more precise tapping on small screens.

**Standard:** The audit skill's 44 × 44 px usability goal. This does not, by
itself, establish failure of WCAG 2.2 AA's different target-size criterion.

**Recommendation:** Apply a 44 px minimum interactive height on small/touch
layouts, including formatting actions, filters, sign-out, and the theme button.
Verify the actual hit area and spacing in the browser.

**Suggested command:** `$impeccable adapt mobile controls`.

### 8. [P2] Initial loading includes every route and a large font asset

**Category:** Performance.

**Locations:** [router.tsx](../web/src/app/router.tsx), static page imports;
[theme.ts](../web/src/app/theme.ts), lines 3 and 153–159.

The production build emits a single **881.49 kB JavaScript entry (267.83 kB
gzip)** and an **874.71 kB variable TTF**. All route pages are imported eagerly.
The font uses `font-display: swap`, which helps text appear but does not reduce
the transfer size. These are build artifact sizes, not measured network totals
or a measured Core Web Vitals failure.

**Impact:** First visits on constrained networks/devices download and process
more than the currently selected page needs.

**Standard:** Performance engineering; not a WCAG finding.

**Recommendation:** Introduce focused route-level lazy loading with appropriate
loading/error states and evaluate a licensed WOFF2 font with needed language
coverage. Measure initial transfer and rendering before deciding whether further
optimization is worthwhile. No evidence here justifies blanket memoization.

**Suggested command:** `$impeccable optimize initial loading`.

## Patterns and positive findings

The main recurring problems are using accent/fill colors as text colors,
coupling semantic markup to visual typography, and assuming compact desktop
controls also meet the touch-target goal. Dashboard summaries also need fixture
coverage for mixed statuses and non-actionable states.

Preserve these strengths:

- Centralized theme creation, shared page components, and MUI controls; most
  styling already uses tokens or theme-aware functions.
- Status text remains visible alongside color. Dark status chips explicitly
  remap several hues instead of blindly reusing light-mode colors.
- MUI automatically links DialogTitle to Dialog's accessible name in this
  installed version: missing handwritten `aria-labelledby` is **not** a defect.
- Inputs have labels, required indicators, and associated helper/error text.
  Save failures preserve input; pending saves disable controls.
- Loading states use named progress indicators and status text; API errors offer
  Retry. Missing and foreign application handling is present.
- Responsive grids, stacked form fields, a mobile drawer, and constrained
  scrollable Add/Edit dialogs are implemented.
- Settings previews are explicitly labeled. Their unimplemented controls are
  not reported as broken features.
- No custom layout-read/write loop, broad `will-change`, unbounded blur effect,
  or heavy animation system was found in reviewed UI source. A short 1 px card
  hover translation alone is not evidence of a serious motion-accessibility defect.
